# 第一次接入：安装 → 初始化眼 → 在AI里直接问

眼的日常入口是Codex、Claude Desktop、Cursor、Proma等AI软件中的MCP。只在第一次安装、微信账号初始化或故障恢复时，需要打开眼自己的界面。

```text
你在AI软件提问
      ↓
AI调用眼的MCP工具
      ↓
眼连接本机服务（需要时后台启动）
      ↓
读取指定群/人物/时间的索引和已下载附件
      ↓
带来源与覆盖边界返回给AI，AI完成总结
```

## 已经在使用原项目

1. 解压眼到单独文件夹，保留原来的安装和数据。
2. 安装Node.js 22+，双击`install.cmd`安装Node依赖。
3. 首次设置会检查常见安装位置。若已完成登录和索引，可跳过重新初始化。程序不在常见位置时，把程序文件的真实路径传给 `node src/cli.js config --yan-exe`。
4. 生成新MCP配置并替换AI客户端中的旧扩展入口。多个扩展同时提供相同微信工具时，建议在客户端停用不再使用的旧入口，避免AI混选；眼不会替你改客户端配置。
5. 在AI里说：“列出最近活跃的群聊，帮我总结其中××群今天的讨论。”

## 一台尚未安装的Windows电脑

1. 安装 Node.js 22+。
2. 向组件提供者取得可用且允许使用的新组件或续期，并按其说明准备本机服务。**不要重新安装旧整合包的固定 WxLens 4.3.0 安装器**；自 2026-10-19 起，眼的安装和整合打包入口已停止准入该文件。
3. 解压源码包，双击 `install.cmd` 安装 Node 依赖。没有可用组件时设置会停止，不会把“安装器哈希一致”当成“组件可用”。
4. 自定义安装位置用 `node src/cli.js config --yan-exe "实际程序路径"` 配置，再运行 `node src/cli.js doctor --native`。
5. 仅首次账号初始化缺失时按原组件界面完成初始化；已有配置的机器按[保配置迁移步骤](component-recovery.md)处理。
6. 生成并合并 MCP 配置，重新加载后用 `npm run verify:live -- --query` 验收实际会话读取。

源码 ZIP 不包含安装器。目前没有已验收且允许公开分发的替代整合安装器。旧文件未签名，SHA-256 只确认文件身份，不能证明当前组件可用或认证有效。4.7.2 仅有本机试用与读取证据，不能代替新电脑首次初始化和再分发验收。

## Codex配置示例

在眼目录执行：

```bash
node src/cli.js mcp-config --client codex
```

输出类似以下TOML，使用命令实际生成的本机路径合并进Codex MCP配置：

```toml
[mcp_servers.yan]
command = "C:/Program Files/nodejs/node.exe"
args = ["D:/Tools/yan/src/server.js"]
startup_timeout_sec = 30
```

MCP的command是`node`，args指向`src/server.js`。不需要网页URL，不需要额外后台控制台，也不要把`setup`当作MCP命令。`setup`需要本人操作；`server.js`只处理stdio协议。

## 常见情况

| 现象 | 处理 |
|---|---|
| AI能看到工具，查询提示服务未就绪 | 先运行 `node src/cli.js doctor --native` 区分服务、原生初始化与账号配置；已有配置不要直接重新登录或取钥。仅首次初始化缺失时运行setup；MCP握手成功不代表索引已就绪 |
| 健康接口正常，查询仍失败 | 查看doctor中的数据库查询检查；HTTP在线不等于数据库已连接或查询就绪。新版 `queryReady=false` 明确未就绪；旧版没有状态接口时通过实际查询确认 |
| 设置或整合打包返回 `YAN_INSTALLER_WITHDRAWN` | 旧 4.3.0 固定安装器已停止准入；保留原配置，按[恢复步骤](component-recovery.md)取得可用组件或续期，源码升级本身不能续期第三方 DLL |
| 原生诊断返回 `YAN_NATIVE_PROTECTION_FAILED` / `-101` | 原生组件在打开数据库前失败；保留配置与 DLL 哈希。已报告的旧 4.3.0 构建含 `expired/self-destruct` 日志；其他构建须另核，不能仅凭 -101 推断到期规则。向组件提供者取得可信更新或续期 |
| 原生诊断返回 `YAN_NATIVE_INIT_FAILED` | 原生运行时或带认证的上游初始化未完成，需用组件诊断入口核对；旧版是 `InitProtection` 通过但 `wcdb_init` 失败，不代表微信密钥失效 |
| 默认位置找不到眼 | 用`config --yan-exe`指定实际程序路径 |
| 已在使用其他端口 | 用`config --base-url http://127.0.0.1:端口`；只允许回环IP |
| 不想自动启动眼 | 在MCP启动环境设`YAN_AUTO_START=false`；之后自行打开服务 |
| 群聊可读、附件找不到 | 明确配置包含`db_storage`的账号目录，确保文件已在微信中下载；多个账号不得自动混选 |
| 登录后仍没有记录 | 等待眼的索引完成，核对所选账号、日期和本地留存情况；扫码本身不能证明所有历史都已获取 |
| 工具超时 | 初次后台启动额外等待约25秒（启动后的连接轮询预算）。大型批量/OCR任务需调高AI客户端工具超时或缩小本轮范围 |
| 路径移动后MCP启动失败 | 在新位置重新运行`mcp-config`并替换客户端路径 |

`doctor --native` 使用受信任的 Windows 安装中的 Electron 和原生组件。旧版调用 `InitProtection`，通过后检查 `wcdb_init`；带认证的新版必须通过上游正常 `WcdbClient.initialize` 入口，不跳过认证。探测不加载账号配置、不读取密钥、不打开聊天数据库、不回传子进程日志；新版认证探测使用隔离配置。它仍会执行已安装组件代码，两个初始化步骤通过也不能替代真实消息读取验收。布局不支持时明确返回可选/未探测；MCP 的普通 `yan_diagnose` 不会自动执行这项探测。

## 已有密钥与新版组件

同一账号、现有数据库和 Windows 用户环境通常可复用已初始化的密钥。换账号、重建数据库或更换加密材料时可能需要重新初始化；不能把服务启动失败或原生保护错误一概归为密钥失效。2026-10-09 的 4.7.2 本机试用由原程序迁移旧 `safe:` 密钥为受保护格式，实际有界读取通过，无重新取钥。

4.7.2 另有独立组件认证，内置初始认证到 2027-01-01 00:00（UTC+8）。到期由组件提供者的正常机制续期，不改系统时间、不移除认证。该未签名候选只经本人批准在本机试用，未纳入公开整合包；旧整合包固定的 4.3.0 安装器现已停止安装和整合打包准入。

日常打开已有眼用 `node src/cli.js open`。CLI/MCP/自有文档统一叫眼，第三方原 EXE、数据路径和署名保留；同文件 `yan.exe` / `眼.exe` 别名会还原为原启动入口，避免改变初始化身份。

所有密钥处理均在眼的本机流程中进行；不要把密钥粘贴到聊天、MCP参数、GitHub Issue或导出包。眼的设置只需要程序路径、服务地址及可选附件目录。
